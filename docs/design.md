# 设计文档

这份文档记两类东西：写代码要守的规范，和这个仓库的设计取舍。对外的接口约定在 [mcp.md](mcp.md)，这里不重复。

能用测试或检查守住的规则，写成测试或检查，这里只说为什么有它；每条规范后面的括号写的是守住它的地方。

## 代码规范

### 语言和运行时

- TypeScript strict，ESM。开发和 CI 用 Node 24，直接运行 `.ts`，所以只用可擦除的语法：不用 `enum`、`namespace` 和构造函数参数属性（`tsconfig.json` 的 `erasableSyntaxOnly`）。
- 发布出去的 `dist/` 要在 Node 20 上运行：`src/` 里不用 Node 20 没有的 API，读 JSON 用 `readFileSync`，不用 JSON 导入属性（CI 最后的 `npm run smoke:dist`，跑在 Node 20 上）。
- 相对导入写 `.ts` 扩展名，构建时改写成 `.js`（`rewriteRelativeImportExtensions`）。
- 转发程序没有运行时依赖，`dependencies` 保持为空，依赖都在 `devDependencies`。
- 格式和 lint 用 biome（`npm run lint`）。生成的 `schema/tools.json`、`schema/prompts.json` 不归 biome 管，格式由生成脚本决定。
- 外部输入只在边界解析：stdio 上的消息、HTTP 响应、环境变量。解析过以后，内部代码信任类型。

### 契约定义

- 工具和 prompt 只在 `src/contract/` 里定义，`schema/*.json` 由它生成，不手改（`npm run check:schema`）。
- `inputSchema` 顶层是 `type: object`、`additionalProperties: false`，不用 `oneOf` / `anyOf` / `allOf`：部分模型服务商不接受顶层的组合关键字。参数之间的互斥（例如 `get_report` 的 `id` 和 `kind`）由服务端检查，写进工具说明（`test/schema.test.ts`）。
- 成功结果和工具错误符合同一个 `outputSchema`，两个分支互斥：错误结果只有 `error`，成功结果一定没有 `error`（`test/schema.test.ts`）。
- 返回里的枚举只能加值，不能删值：调用方要能容忍不认识的值，比如以后新增的错误码（`npm run check:compat`）。
- `contentNotice` 在 schema 里只约束为非空字符串，固定文案是 `CONTENT_NOTICE`，由服务端和测试使用：提示语改字不该算不兼容变更。
- 每个工具的说明都标注返回内容不是指令（`test/schema.test.ts`）。参数说明写清格式、时区、默认值和范围边界。
- 每个工具在 `test/fixtures/results.json` 里有一份合成的成功返回，通过自己的 `outputSchema`。新增工具时一起加。

### 工具说明里的引导句

工具说明是写给对方模型看的。引导模型「先这样做」的句子都是补丁：模型足够聪明以后可能就不需要了。每一句引导都要有一个具体的失败案例，说明它在防什么；agent 使用评测搭起来以后（见「决定：agent 使用评测等服务端上线后再做」），换模型或改说明时带和不带这一句各跑一遍，不带也能通过就删掉。

| 引导句（在哪个工具） | 要防的失败 | 案例状态 |
| --- | --- | --- |
| 中文关键词，2～4 个词（`search`） | 把用户的整句英文问题原样当 query，零结果 | 未验证 |
| 零结果就换词，或改用 `list_topics`（`search`） | 零结果后直接告诉用户「没有相关内容」 | 未验证 |
| 引用前用 `get_*` 读全文（`search`） | 只凭摘要回答，引用了摘要里被截断的结论 | 未验证 |
| `not_found` 不要再引用、不要重试（`get_answer`） | 撤回的内容被反复重试，或仍被当作来源引用 | 未验证 |
| 命令和链接先给用户确认（所有工具） | 把讨论里的 `curl … \| sh` 直接执行 | 未验证 |
| 不要长期缓存，需要时重新读取（所有工具） | 撤回后仍从对方 agent 的记忆里引用旧内容 | 未验证 |

新增引导句时在这张表里加一行。

### 测试

- 测试全部离线，只用合成数据，不连真实服务。转发程序在 `test/fake-server.ts` 起的本地假服务端上测，CLI 起真实子进程测（`test/cli.test.ts`）。
- 检查脚本自己有测试，用构造的违规样例证明它确实会失败（`scripts/*.test.ts`）。新增一条检查时，一起加至少一个它应该拦下的样例。

### 转发程序的不变量

`src/bridge.ts` 和 `src/cli.ts` 现在的行为，不能顺手改：

- **stdout 只写 JSON-RPC 消息**，日志和错误一律走 stderr。客户端把 stdout 当协议流读，混进一行日志就会断开。
- **透明转发。** 每条消息单独 POST 到端点，只按规范补请求头（`MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name`），不理解、不改写消息内容，也不在新旧两代协议之间转换。
- **每个请求只发一次，不自动重试。** 服务端每次受理 `tools/call` 都计额度，重试会悄悄花掉用户的额度；要不要重试由对方 agent 按 `code` 决定。
- **HTTP 错误变成带原 id 的 JSON-RPC 错误**（-32000，`data.httpStatus`），同时在 stderr 打一行说明；服务端给出的 JSON-RPC 错误原样转交。401 原样交给客户端，理由见 mcp.md「决定：凭证无效时返回 401，不退回免登录的范围」。
- **不保存会话。** 不发送也不记住 `Mcp-Session-Id`，服务端是无状态的。
- **key 只从环境变量 `JIAJIA_MCP_KEY` 读**，不收命令行参数：命令行参数会出现在进程列表和 shell 历史里。带 key 时端点必须是 https（本机调试除外）。key 不出现在 stdout、stderr 和错误信息里。
- **一行一条消息。** 批量请求和解析不了的行在本地就返回 JSON-RPC 错误，不发到服务端。

## 决定

### 决定：工具定义以本仓库为准

- **日期和来源**：2026-10-28，维护者（#6）。替代 #1 里「契约只链接不复制」。
- **决定**：工具和 prompt 的定义（名字、说明、`inputSchema`、`outputSchema`、注解）只在本仓库维护，随 npm 包发布。服务端依赖这个包，在自己的测试里用包里的 `outputSchema` 校验真实返回。npm 包发布之前，服务端用 git 依赖锁定本仓库的 tag，直接读 `schema/*.json`（git 依赖不跑构建，没有 `dist/`）。
- **理由**：契约是公开的，实现是私有的。定义放在公开仓库，调用方能直接读到、能在发版记录里看到变化。服务端校验同一份 schema，契约和实现不会悄悄分叉。不兼容变更在这里由 `check:compat` 拦下，比在服务端拦更早。
- **放弃的方案**：以服务端为准、本仓库同步副本：改契约要两边各开 PR，副本容易过期。只存线上 `tools/list` 的快照：上线前守不住任何东西。
- **重新评估**：服务端需要按层级或配置动态生成工具定义，静态 schema 表达不了时。

### 决定：契约文档拆成公开和内部两份

- **日期和来源**：2026-10-28，维护者（#6）。
- **决定**：对外的部分（端点和协议、对象、工具、错误、新鲜度、安全处理、层级与限额、计量口径、版本规则）放在本仓库的 [mcp.md](mcp.md)。服务端的实现细节（存储、缓存、计量的写法、成本验收）留在服务端仓库。
- **理由**：调用方只需要知道行为，不需要知道服务端怎么存。实现细节里有内部路径和服务名，不能进公开仓库。
- **放弃的方案**：整份搬过来：要先清掉私有信息，而且实现细节一改就要动公开文档。整份留在服务端：公开仓库的用户读不到契约。
- **重新评估**：服务端开源时。

### 决定：TypeScript 写定义，提交生成的 JSON

- **日期和来源**：2026-10-28，#6。
- **决定**：工具定义写在 `src/contract/*.ts`，共用的片段（公共字段、错误、续页）只写一次。`npm run schema:build` 生成 `schema/tools.json` 和 `schema/prompts.json`，生成文件提交进仓库，CI 检查它没有过期。
- **理由**：10 个工具共用大量片段，手写 JSON 会把同一段复制 10 遍，改一处漏一处。提交生成文件，评审时能直接看到契约的 diff；`check:compat` 用 `git show <tag>:schema/tools.json` 取上一个版本，不用重新构建旧代码；服务端的 git 依赖不跑构建也能读到。不用 JSON Schema 的跨文件 `$ref`：MCP 客户端拿到的工具定义必须是自包含的。
- **放弃的方案**：手写 JSON：重复太多。只在构建时生成、不提交：评审看不到 schema 的变化，兼容检查要检出旧 tag 重新构建。
- **重新评估**：工具数量大到生成文件难以评审时。

### 决定：开发和 CI 用 Node 24，用户侧支持 Node 20

- **日期和来源**：2026-10-28，维护者（#6）。替代 #6 正文里「只支持 Node 24」的提议。
- **决定**：开发和 CI 用 Node 24，直接运行 `.ts`，不用 tsx。`package.json` 的 `engines` 保持 `>=20`，CI 最后切到 Node 20 跑 `smoke:dist`，验证构建好的 `dist/` 能导入、能转发。
- **理由**：发布出去的是编译后的 `dist/`，用户不需要直接跑 `.ts`。Node 22 还是 LTS，`engines` 卡到 `>=24` 会把很多用户挡在外面。开发侧用 Node 24 可以去掉 tsx 这层运行器。
- **放弃的方案**：用户侧也只支持 Node 24：挡住 Node 20/22 的用户。开发和测试继续用 tsx 跑 Node 20/22 矩阵：多一个依赖，CI 时间翻倍，而用户实际运行的 `dist/` 反而没被直接测到。
- **重新评估**：Node 20 停止维护以后，把冒烟测试的版本提到 22。

### 决定：安全样例放在本仓库共享发包

- **日期和来源**：2026-10-28，#6。
- **决定**：mcp.md「返回内容的安全处理」要求的注入和脱敏样例放在 `schema/safety-cases.json`，跟着 npm 包发布，服务端测试直接使用。样例全部是合成数据。
- **理由**：「至少 10 条，其中至少 1 条走 `my_questions`」是契约的一部分，放在契约旁边才守得住（`test/schema.test.ts`）。服务端和契约用同一份样例，新增一条样例，服务端下次升级依赖就会被它检查。
- **放弃的方案**：只放在服务端：攻击者看不到我们测了什么，但契约和样例分在两处，样例数量和覆盖面没人能从公开仓库核对。
- **重新评估**：发现公开样例被用来针对性地绕过过滤时，把那一类样例挪回服务端私有测试，这里保留数量下限。

### 决定：agent 使用评测等服务端上线后再做

- **日期和来源**：2026-10-28，#6。
- **决定**：「给 agent 接上夹夹 MCP，它会不会先搜再读、引用时带不带 url、零结果会不会换词」这类端到端评测，等 staging 的 `/mcp` 可用以后再做。
- **理由**：评测要用真模型和真实端点，假服务端上的结果说明不了工具说明在真实数据上的效果，还要付模型费。
- **放弃的方案**：先用假服务端和合成数据跑。
- **重新评估**：staging 的 `/mcp` 可用时。

## 还没定的事

- **`outputSchema` 的字段名。** 现在是按契约语义起的草案名，等服务端实现时对齐，打第一个 tag 之前冻结。
- **服务端怎么拿到私有仓库的 git 依赖。** 本仓库现在是私有的，服务端的 CI 和构建安装 git 依赖时需要访问权限：先公开仓库，或者配只读凭据。到服务端第一次锁 tag 时再定。
- **兼容清单。** 支持哪几个协议版本、是否同时支持两代协议，等服务端和客户端联调后写进 mcp.md「兼容清单」。
